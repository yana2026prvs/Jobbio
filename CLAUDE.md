# CLAUDE.md

Інструкції для Claude Code при роботі в цьому репозиторії. Читай перед початком роботи, оновлюй після кожної помітної зміни (нова секція UI, нова секція сховища, зміна конвенції).

## Що це за проєкт

Односторінковий веб-застосунок (PWA) — трекер 13-тижневого плану виходу на ринок праці для UI/UX дизайнерки. Без білд-кроку, без залежностей, без бекенду. Розмітка, стилі й логіка розкладені по файлах за призначенням (`css/*`, `js/*`), браузер підвантажує їх напряму через `<link>`/`<script>` — жодного бандлера чи транспайлера.

Детальний опис фіч і сторінок — у [README.md](README.md) (українською, актуалізований README — головне джерело правди для user-facing опису та повної файлової структури). Цей файл (CLAUDE.md) — для розробницьких конвенцій і контексту, які в README не пишуть.

## Структура репозиторію

```
.
├── index.html          # тільки розмітка (4 сторінки: Plan/Apps/Skills/Profile) + <link>/<script> теги
├── css/                # base.css (спільний chrome/токени) + по файлу на сторінку/область
├── js/                 # по файлу на функціональну область, детально в README "Структура"
├── manifest.json       # PWA-маніфест
├── sw.js               # service worker (офлайн-кеш; ASSETS список тримати синхронним з css/js; index.html — network-first, решта — stale-while-revalidate, див. нижче)
├── serve.py            # локальний static-сервер (навмисно не використовує http.server CLI — див. докстрінг)
├── icons/              # іконки для home screen (192/512/apple-touch)
├── img/                # декоративні ілюстрації для UI (не PWA-іконки), тримати сжатими (sips -Z) і в sw.js ASSETS
├── tests/index.html    # браузерні автотести (без npm/jsdom)
└── .claude/launch.json # конфіг dev-сервера для Browser preview (`serve.py`, порт 8000)
```

Повний список `css/*`/`js/*` файлів і що в кожному лежить — у [README.md](README.md#структура), не дублюю тут, щоб не розсинхронізувалось.

## Важливо про js/*: спільна глобальна область видимості, не ES-модулі

Файли в `js/` **не** використовують `import`/`export` — це звичайні `<script>`-теги, і всі `var`/`function` верхнього рівня стають глобальними (так само, як раніше все було в одному `(function(){...})()`). Це свідомий вибір заради простоти (без бандлера немає зручного способу перевірити відсутні `import`), а не недогляд.

Ключове правило, яке звідси випливає: **жоден файл, крім `js/app.js`, не повинен викликати рендер/завантажувальні функції на верхньому рівні** (тобто не всередині функції чи `addEventListener`-колбека) — лише оголошувати `function`/`var`. Усі реальні виклики ініціалізації (перше `loadX()`/`renderX()` для кожної сторінки) зібрані в `js/app.js`, який підключається останнім, коли всі інші файли вже оголосили свої функції. Причина: деякі функції (напр. `renderCalendar()` в `js/plan.js`) звертаються до змінних з інших файлів (`apps` з `js/apps.js`), і якщо викликати їх одразу при завантаженні файлу, а не відкласти до `app.js`, браузер кине `ReferenceError`, бо той файл ще не встиг завантажитись.

Той самий ReferenceError-ризик стосується й **top-level викликів функцій з інших файлів** (не лише рендер-функцій) — наприклад, `setupHeaderPanel(...)` у `js/plan.js`/`js/skills.js` викликається одразу при завантаженні файлу (це просто підписка на `addEventListener`, не рендер, тож правило вище її не забороняє), але сама функція `setupHeaderPanel` оголошена в `js/header.js`. Тому `js/header.js` підключений **другим** у `index.html` (одразу після `js/utils.js`), а не в кінці — він без залежностей, і кілька інших файлів звертаються до його функцій на своєму верхньому рівні. Якщо новий спільний "chrome"-хелпер потрібен кільком файлам одразу при завантаженні (не лише всередині колбеків) — клади його рано в порядку `<script>`-тегів, а не покладайся на те, що "рендер-виклики й так усі в app.js".

Якщо додаєш нову функціональну область (новий файл `js/whatever.js`): онови `index.html` (`<script src>` + за потреби `<link>` на новий CSS) і `sw.js` (`ASSETS`), і додай сюди ж (і в README) короткий опис файлу.

## PWA service worker і "старі" правки в реальному браузері

`sw.js` реєструється (`js/register-sw.js`) у **будь-якому** браузері, що відкривав застосунок — не лише в Browser-тулах цієї сесії. Якщо після CSS/JS-правки користувачка каже щось на кшталт "лого злетіло" / "стара версія" / "не бачу змін" — це майже завжди stale service-worker cache в ЇЇ браузері, а не регресія в коді (спершу все одно звір з git diff, що джерело правильне). `index.html` — network-first (оновлюється одразу), але `css/*`/`js/*`/`img/*` — stale-while-revalidate: перший показ після правки все ще стара версія, і потрібне **друге** перезавантаження сторінки, щоб побачити свіжу (перше підтягує нове у фоні й оновлює кеш, друге вже його показує). Якщо і після другого перезавантаження стара версія — попроси користувачку зробити hard refresh (Cmd+Shift+R) або в DevTools → Application → Service Workers → Unregister, і презавантажити.

## Запуск і перевірка

- Локальний перегляд: `python3 serve.py` — сервер на `http://localhost:8000`.
- **Не використовуй** `python3 -m http.server` напряму — його argparse викликає `os.getcwd()`, що падає в пісочниці (`PermissionError`). Завжди `serve.py`.
- **Browser-тули `preview_start` з `name: "jobbio"` (`.claude/launch.json`) стабільно падають** з `Operation not permitted` — пісочниця блокує сам спавн процесу через цей тул (не залежить від порту чи `os.getcwd()`; `serve.py` тепер підтримує `PORT` з env і в `launch.json` увімкнено `autoPort`, але це не допомагає, бо файл узагалі не вдається виконати цим шляхом). Робочий обхід: піднімай сервер напряму через Bash (`nohup python3 /Users/anaprideus/Documents/Claude/Jobbio/serve.py > /tmp/....log 2>&1 &`), а в Browser-тулах відкривай прев'ю через `preview_start` з `url: "http://localhost:8000/..."` (не `name`). Не витрачай час на повторні спроби `name: "jobbio"` — одразу йди цим шляхом. Якщо стара фонова копія `serve.py` лишилась з минулої сесії й тримає порт 8000 — `lsof -i :8000 -sTCP:LISTEN` і `kill <PID>` перед новим запуском.
- Тести: відкрити `http://localhost:8000/tests/` у браузері (не подвійним кліком — тестам потрібен спільний origin з `index.html` через iframe, а `file://` його не дає). Тести вантажать реальний `index.html` у прихований iframe і перевіряють логіку дедлайнів, воронку відгуків, рендер, localStorage, міграцію старих даних.
- Для UI-змін: підняти прев'ю через `preview_start` з `url: "http://localhost:8000/..."` (див. вище — не `name`), перевірити фічу візуально перед тим, як звітувати про завершення.
- **Browser pane агресивно кешує CSS/JS між правками** — після редагування файлу в `css/*`/`js/*` звичайний `navigate` на той самий URL, `location.reload(true)` і навіть `Ctrl+Shift+R` в цій вкладці далі віддають СТАРИЙ вміст (`serve.py` не шле `Cache-Control`/`ETag`, а сама пісочниця кешує ще агресивніше за heuristic freshness). Симптом: `getComputedStyle(...)` показує старе значення, хоч `curl http://localhost:8000/css/....css` вже віддає нове. Робочий обхід — перепідключити самі `<link rel=stylesheet>` (не сторінку) з cache-busting query через `javascript_tool`, і лише тоді знімати скріншот/читати computed style:
  ```js
  var links = [...document.querySelectorAll('link[rel=stylesheet]')];
  Promise.all(links.map(link => new Promise(res => {
    var clone = link.cloneNode();
    clone.href = link.href.split('?')[0] + '?t=' + Date.now() + Math.random();
    clone.onload = () => res('ok'); clone.onerror = () => res('err');
    link.after(clone); link.remove();
  })));
  ```
  Для змін у `js/*.js` аналогічно не допоможе просте `navigate` — потрібен повний `navigate` на URL (не той самий, що вже відкритий) або новий tab (`tabs_create`), бо `<script>` не можна безпечно "перепідключити" без ризику подвійної ініціалізації (`app.js` повторно викличе рендер-функції на вже живому DOM).

## Технічний стек і конвенції коду

- Ванільний HTML/CSS/JS, `var`-стиль функцій (не ES-модулі, немає bundler). Дотримуйся наявного стилю — не додавай TypeScript/JSX/фреймворки.
- Дизайн зараз — світла Jobbio-style тема (див. коміт `745ede7`); попередня темна "midnight navy" тема замінена. Перевіряй актуальний вигляд у браузері, README міг не встигнути оновитись.
- Дані живуть виключно в `localStorage` браузера, префікс ключів `job-*` (напр. `job-plan-statuses-v1`, `job-applications-v1`, `job-skills-v1`, `job-profile-v1`, `job-learning-plans-v1` і супутні). При додаванні нового стану — новий ключ з суфіксом `-v1`, і функції `loadX`/`saveX` за наявним патерном (`try/catch` навколо `localStorage`, JSON serialize).
- Кожна логічна секція (Plan / Apps / Skills / Profile / learning-plan) має свій `loadX`/`saveX`/`renderX` набір у своєму файлі під `js/` (див. секцію про структуру вище) — тримайся цього поділу, не змішуй стан різних секцій і не переноси функцію в інший файл без потреби.
- Розбір завантажених планів навчання (`.docx`/`.txt`/`.md`) — евристичний парсинг заголовків, `.docx` довантажує JSZip з CDN лише за потреби (`ensureJSZip`). Не ламай офлайн-роботу `.txt`/`.md`-шляху.
- **Шкала відступів (правило зовнішнього/внутрішнього, proximity)** — CSS-змінні в `css/base.css` (`:root`): `--space-tight` (8px) і `--space-tight-lg` (12px) для елементів, які напряму формують одну групу (рядки картки, чіпи одного фільтра, список карток); `--space-group` (16px) для відступу між групами, обʼєднаними в одну секцію (напр. фільтр→дошка, кілька блоків усередині `.hero-card`); `--space-section` (20px) для відступу між найвищими за ієрархією секціями сторінки (`.sh-large`, `.hero-card`→`Дедлайни`, `.profile-card`→`.profile-section`). Мікро-відступи всередині складених елементів (іконка+текст, label+input, padding чіпа) у цю шкалу свідомо не вписані — це не "групи компонентів", а одна складова одиниця. Новий блок на сторінці — вибирай тир за тим, на якому рівні ієрархії він сидить, не хардкодь px.

## Коли звертатись сюди

- Перед будь-якою зміною коду — звірся зі структурою і конвенціями вище.
- Після завершення task — онови цей файл, якщо змінилась структура, конвенції, команди запуску, або з'явилась нова секція/фіча, про яку варто знати наперед.
